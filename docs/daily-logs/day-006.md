## Key Decisions

### LED Control Architecture
Created `src/led_control.c` with centralized GPIO33 ownership:
- **Auto mode**: main loop heartbeat controls LED (solid on when WiFi connected)
- **Manual mode**: API sets LED state, heartbeat becomes no-op
- Prevents race condition between main loop and API writes

### Integer-Only JSON
`CONFIG_CBPRINTF_FP_SUPPORT` is off (minimal libc). All JSON values are integers:
- FPS × 10 (e.g., `"fps":20` = 2.0 FPS)
- Temp × 10 (e.g., `"temp":250` = 25.0°C)
- JavaScript frontend divides by 10 for display

### k_busy_wait → k_yield Fix (Critical)
**Root cause**: ESP32 runs in unicore mode. `k_busy_wait()` is a CPU spin loop that
blocks ALL threads — including WiFi/TCP stack. During continuous MJPEG streaming,
the capture loop's busy-waits starved the network, causing 0 bytes received by clients.

**Fix**: Replaced `k_busy_wait(10)` with `k_yield()` in VSYNC and frame_done wait loops.
`k_yield()` allows higher-priority threads (WiFi, TCP) to process between DMA polls.
Kept `k_busy_wait(500)` for the short post-frame drain delay only.

**Note**: `k_usleep()` was tried first but has 10ms minimum resolution (system tick),
which is too coarse for VSYNC timing and caused capture to miss frame boundaries.
