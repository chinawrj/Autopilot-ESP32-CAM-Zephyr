## Architecture Decisions

- **Manual SCCB probe first**: Skip Zephyr's ov2640.c driver — CONFIG_VIDEO adds ~2MB
  static heap, and our DRAM is at 94.77%.
- **SRAM DMA buffers**: Original ESP32 cannot DMA directly to PSRAM from I2S.
  Use 4×1024B SRAM ring buffer + CPU copy to 64KB PSRAM frame buffer.
- **Standalone capture module**: Custom I2S camera driver (`cam_i2s_capture.c`)
  feeding `frame_source` abstraction, not full Zephyr video API.
- **Pre-capture header extraction**: Run DMA for 200ms before warmup to capture
  canonical JPEG header (605 bytes: DQTs + DHTs + SOF0 + SOS). This avoids the
  DMA restart timing gap that loses 50–600 bytes of header per frame.

## What Was Done

### Task 1: XCLK + PWDN + SCCB Communication

- XCLK: 20MHz via LEDC PWM on GPIO0
- PWDN: GPIO32 deasserted (LOW) with 100ms delay
- SCCB probe: OV2640 detected — PID=0x26, VER=0x42

### Task 2: OV2640 JPEG Configuration

- Applied full `ov2640_settings_jpeg3` register table from esp32-camera project
  (14 entries including 8 undocumented DSP registers)
- IMAGE_MODE = 0x12 (JPEG_EN | HREF_VSYNC)
- RESET = 0x14 (RESET_JPEG | RESET_DVP)
- Clock: CLKRC=0x00 (no doubler), R_DVP_SP=0x08 (pclk_div=8, auto off)

### Task 3: I2S Camera Capture Driver

- Custom I2S0 peripheral in camera mode (`cam_i2s_capture.c`, ~850 lines)
- 4×1024B DMA ring buffer in SRAM → CPU copy to 64KB PSRAM frame buffer
- VSYNC GPIO25 interrupt for frame sync (rising edge = blanking start)
- **GPIO matrix fix**: H_SYNC ← const HIGH, H_ENABLE ← HREF (was swapped)
  - H_ENABLE gates I2S data capture per line; original config captured blanking data

### Task 4: JPEG Header Reconstruction

- **Problem**: DMA restart after VSYNC takes ~50µs, losing ~130–600 bytes of
  JPEG header (SOI, DQTs, sometimes DHTs, sometimes SOF0)
- **Solution**: Pre-capture pass runs DMA for 200ms to capture continuous frame data
  containing complete JPEG headers. Extract and save canonical header (605 bytes).
- **Smart injection**: Match first captured marker against saved header using 6-byte
  sequence match. Inject only the missing prefix. Handles variable data loss:
  - Only DQTs lost → inject SOI + DQTs (140 bytes)
  - DQTs + DHTs lost → inject SOI + DQTs + DHTs (572 bytes)
  - All of the above → inject entire saved header
- OV2640 doesn't output SOI or EOI markers — both are synthesized

### Task 5: MJPEG Streaming Integration

- `frame_source.c` probes camera on init, falls back to test pattern
- `cam_i2s_capture_frame()` → MJPEG stream at `/stream/tcp`
- Warmup: 30 frames initial, 2 frames for streaming
- **Verified**: 320×240 JPEG decoded by Python PIL, all markers present
  (SOI → DQT×2 → DHT×4 → SOF0(320×240) → SOS)

## Key Findings

1. **GPIO matrix swap was critical**: Without the H_SYNC/H_ENABLE fix, I2S captured
   blanking data between lines, corrupting JPEG stream
2. **DMA restart gap is inherent**: Polling-based Phase 2 start loses ~50µs, ISR-based
   was worse (32+ stale bytes). Solved by pre-capture header extraction instead.
3. **OV2640 JPEG frame structure**: No SOI/EOI, DQT tables are deterministic per QS
   register setting, header is ~603 bytes (DQT→SOS)
4. **Image is dark**: Mean RGB ~13,18,8 — exposure/gain tuning needed (Day 5)
5. **net_pkt alloc failure**: Occurs during sustained streaming — may need larger
   net_buf pool or frame rate limiting
