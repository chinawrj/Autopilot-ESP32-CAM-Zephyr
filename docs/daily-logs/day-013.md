## Design

### HTTP Subsystem Split (1110 → 4 files)

| File | Responsibility | Target |
|------|---------------|--------|
| `ws_protocol.c/h` | SHA1, WebSocket handshake, WS frame send | ~150 lines |
| `stream_service.c/h` | Stream worker thread, MJPEG/WS/snapshot handlers, stream state + stats API | ~280 lines |
| `http_routes.c/h` | Page handlers, API handlers, path dispatch | ~280 lines |
| `http_server.c` | Core: sockets, accept loop, request parsing, thread management | ~280 lines |

Key design decisions:
- Stream state (sem, fd, mode, fps, frame_cnt) owned by `stream_service` behind API
- Handoff via `struct stream_request` instead of loose globals
- `ws_pending_key` passed atomically in request struct
- SHA1/WS functions keep `__attribute__((noinline))` for stack control

### Camera Subsystem Split (853 → 3 files)

| File | Responsibility | Target |
|------|---------------|--------|
| `cam_i2s_hw.c/h` | GPIO/peripheral config, DMA setup/start, ISR | ~280 lines |
| `cam_jpeg_fixup.c/h` | Header extraction, JPEG reconstruction, EOI fixup, debug dump | ~250 lines |
| `cam_i2s_capture.c` | High-level capture API, warmup, public interface | ~200 lines |

Key design decisions:
- No extern globals for cross-module access — pass buffers/state explicitly
- Hardware module exposes: init, dma_start, dma_stop, ISR state accessors
- JPEG fixup module is pure functions (buffer in, buffer out)

## Implementation Order
1. Extract `ws_protocol.c/h` (cleanest cut)
2. Extract `stream_service.c/h` with clean API
3. Refactor `http_server.c` / create `http_routes.c/h`
4. Build + verify HTTP subsystem
5. Extract `cam_jpeg_fixup.c/h`
6. Extract `cam_i2s_hw.c/h`
7. Build + flash + full on-device verification
