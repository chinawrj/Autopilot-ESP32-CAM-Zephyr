# Day 7 — TCP Accept Bug Investigation & Two-Port Fix

## Goals
1. ✅ Diagnose post-HTTP stream connection failure (stream works only as first request)
2. ✅ Implement architectural fix: two-port server (HTTP:80, Stream:81)
3. ✅ Verify fix with comprehensive interleaved HTTP→Stream testing (8/8 pass)

## Milestone: M3 Stream Stability — Complete ✅

## The Bug

After serving any HTTP response (e.g. `GET /`), subsequent `zsock_accept()` on the **same
listen socket** would block forever when a stream client connected. The stream worked perfectly
as the first request but never as a subsequent one.

### Investigation Path

1. **Initial theory — zsock_close() corruption**: Ruled out by testing a "never-close" variant
   that leaked HTTP file descriptors. The bug persisted even without calling `zsock_close()`.
2. **Theory — net_buf exhaustion**: Ruled out by monitoring buffer counts; resources were adequate.
3. **Theory — fd table exhaustion**: `CONFIG_ZVFS_OPEN_MAX` was 4 (default). Raised to 16.
   This fixed secondary fd-exhaustion crashes but not the core accept bug.
4. **Deep trace of Zephyr TCP internals**: `zsock_accept_ctx` → `zsock_wait_data` →
   `k_condvar_wait(accept_q)` → `tcp_recv` → `tcp_conn_search`. The connection matching
   uses exact (src_ip, src_port, dst_ip, dst_port) tuples. After a client FIN on the
   listen socket's address, the TCP state machine corrupts future accept behavior for
   that listen socket.

### Root Cause (Workaround, Not Patched)

Zephyr's TCP stack (v4.1.0) has a per-listen-socket state corruption triggered by TCP
connection close transitions (FIN → CLOSE_WAIT → LAST_ACK). The corruption prevents new
connections from being accepted on the affected listen socket. This is **not** a resource
exhaustion issue — it's a state machine bug in `zephyr/subsys/net/ip/tcp.c`.

### Zephyr TCP Close Limitations (ESP32)

| API | Behavior |
|-----|----------|
| `setsockopt(SO_LINGER)` | Accepted but silently **ignored** |
| `zsock_shutdown(SHUT_WR)` | Returns `ENOTSUP` |
| `zsock_shutdown(SHUT_RDWR)` | Returns `ENOTSUP` |
| `zsock_shutdown(SHUT_RD)` | Works |

No application-level way to force TCP RST on ESP32 Zephyr.

## Key Decisions

### Two-Port Architecture

Isolated HTTP (port 80) and stream (port 81) onto separate listen sockets:

```
Port 80 (HTTP):  GET / → index page
                 GET /api/status → JSON
                 GET /api/led/* → LED control
                 GET /ws → WebSocket page
                 → Proper wait_for_peer_close() + zsock_close()

Port 81 (Stream): GET /stream/tcp → MJPEG (handed to stream thread)
                  GET /stream/ws → WebSocket (future)
                  → Stream thread owns fd lifetime
```

Single `http_thread_fn` uses `zsock_poll(fds, 2, -1)` to multiplex both listen sockets.
This avoids a second thread while keeping both ports responsive.

### Dynamic Stream URL in HTML

Index page uses JavaScript to construct stream URL dynamically:
```javascript
document.getElementById('cam').src =
  'http://' + location.hostname + ':' +
  (parseInt(location.port || 80) + 1) + '/stream/tcp';
```

This avoids hardcoding the IP address and works regardless of DHCP assignment.

### Buffer Configuration (Reverted to Normal)

Doubled buffers (32/64) during debugging, then reverted to original (16/32) after
confirming the fix is purely architectural, not buffer-dependent.

## Lessons Learned

1. **Zephyr TCP socket reuse is fragile on ESP32**: After client-initiated close, the
   listen socket may become permanently stuck. Isolate different traffic types onto
   separate listen sockets.
2. **"Never close" test is essential**: If leaking fds still reproduces the bug, the
   problem is not in your close() logic — it's deeper in the stack.
3. **SO_LINGER is a no-op in Zephyr**: Don't rely on it for clean shutdown behavior.
4. **ZVFS_OPEN_MAX default of 4 is too low**: Any server with multiple connections needs
   at least 16.
