# Day 12 — Single-Frame Snapshot Endpoint

## Goals
1. Add `/snapshot.jpg` endpoint that returns a single JPEG frame
2. Wire a "Snapshot" button on the index page (opens image in new tab)
3. Verify on-device end-to-end without regressions

## Background

M0–M5 are complete. With the streaming + HUD + LED stack stable, the next
natural product feature is a single-frame snapshot — useful for quick image
capture without consuming a full MJPEG/WebSocket stream slot.

## Design

The camera capture path (`cam_i2s_capture_frame`) is **not thread-safe** — it
uses shared global DMA state. Only the dedicated stream worker thread is
allowed to call `frame_source_get()`.

To stay safe and minimize code changes, snapshot requests are routed through
the same stream worker by introducing a new `STREAM_SNAPSHOT` mode:

```
HTTP listener (:81) — routes /snapshot.jpg
        ↓ stream_client_fd + stream_sem (existing handoff)
Stream worker thread
        ↓ stream_mode == STREAM_SNAPSHOT
handle_snapshot(): one frame_source_get() → image/jpeg response → close
        ↓ existing 3-second cooldown (TCP retransmit drain)
ready for next request
```

This guarantees:
- No camera concurrency (stream worker is the only camera client)
- Active streams correctly return 503 to snapshot requests (existing busy gate)
- Snapshot requests during streams also get 503

## Completed

### `/snapshot.jpg` endpoint
- New `STREAM_SNAPSHOT` enum value in `stream_mode`
- New `handle_snapshot()` function in `http_server.c`:
  - Single `frame_source_get()` call
  - HTTP/1.1 200 with `Content-Type: image/jpeg`,
    `Content-Length`, `Content-Disposition: inline; filename="snapshot.jpg"`,
    `Cache-Control: no-store`, `Connection: close`
  - 256-byte header buffer (initial 160 truncated — see fix below)
- Routed in `handle_stream_client()` on stream port (:81)
- Stream worker `stream_thread_fn()` dispatches `STREAM_SNAPSHOT` to
  `handle_snapshot()`

### Index page UI
- New "Snapshot" button next to LED controls
- `snap()` JavaScript opens `http://<host>:<port+1>/snapshot.jpg?t=<ts>` in a
  new tab; cache-bust query string ensures a fresh capture each click

### Bug found & fixed
- First flash: header buffer of 160 bytes truncated the
  `Connection: close\r\n\r\n` line (computed length ≈165 B). curl reported
  "Nul byte in header" because the body began before the header terminator.
- Fix: bumped buffer to 256 bytes. Re-flashed and verified.

## Files Changed
- `src/http_server.c` — `STREAM_SNAPSHOT` enum, `handle_snapshot()`, dispatch,
  routing on stream port
- `src/html_pages.h` — Snapshot button + `snap()` JS

## Memory Impact
- DRAM: 181,488 B → 181,488 B (no change — header buf is stack-local)
- Flash: 542,468 B → 542,804 B (+336 B for handler + button HTML)

## Notes
- Existing 3-second `STREAM_CLOSE_COOLDOWN_S` applies to snapshots too,
  rate-limiting consecutive snapshots to ≈1 every 3 s. This is intentional —
  the cooldown protects the TCP stack from rapid socket churn.
- For burst-snapshot use cases later, the cooldown could be skipped for
  snapshot mode (short-lived connection), but no need today.
